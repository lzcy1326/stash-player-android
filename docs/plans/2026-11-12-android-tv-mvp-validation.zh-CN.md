# Android TV MVP 技术验证方案

用 **3～5 人日**做一个可侧载的 Debug 原型，验证同一个应用能否复用 Stash 连接和播放能力，让用户在目标电视上只用遥控器完成 **电视桌面启动 → 配置服务器 → 浏览影片 → 播放和跳转 → 返回原卡片 → 重启后续播**。这段工作计入前期估算的 20～32 人日 MVP，验收后再更新剩余工期。

## 验证环境

- **设备**：一个 API 29 或以上的 Android TV 模拟器，加一台实际要支持的 Android TV / Google TV 设备及其原装遥控器。模拟器用于重现焦点和导航问题，真机用于确认遥控器、软键盘、局域网访问和硬件解码。只有模拟器可用时，记录阶段结果，真机兼容性继续待验。
- **服务**：测试 Stash 实例，启用 API Key，准备一个能触发分页的影片列表。使用公开或专用样片，允许写入测试影片的观看记录。测试记录使用设备型号、系统版本、应用提交、Stash 版本和样片编号；录屏、日志及截图遮盖地址、凭据和私有媒体信息。
- **样片**：一段时长至少 3 分钟的 H.264/AAC MP4，用于直连、快进和续播；一段实际由 Stash 提供 HLS 转码的样片；再选一段目标库中常见的高负载样片，例如 4K HEVC。提前在同一 Wi-Fi 下用当前手机版验证样片和接口，并记录各样片实际播放的流。

## 原型实现范围

| 验证点 | 原型做法与现有代码 |
|---|---|
| 电视启动 | 在当前 `app` 增加独立电视 Activity 和 `LEANBACK_LAUNCHER` 入口，声明触屏非必需，配置电视横幅。使用 `tvPreview` 构建电视测试包，保留常规 Debug 构建验证手机入口。 |
| 服务器配置 | 电视页仅提供地址、API Key、测试连接、保存和返回。沿用 `StashServerProfile`、`StashSettingsRepository` 与连接校验逻辑，检查遥控器能打开、使用并退出系统输入法。 |
| 列表和焦点 | 做一个 16:9 影片网格，使用 `StashGraphQlClient.findSceneCardsPage` 读取真实列表。空、加载、错误和重试都保留可操作的焦点；返回时按影片 ID 恢复焦点与滚动位置。列表卡片直接打开播放。 |
| 遥控器播放 | 从 `GraphQlStashStreamResolver` 取播放流，使用 `StashPlayerController` 和 `PlayerSurface` 渲染。保留 TV 自己的播放控件与按键分发。控件隐藏时，确定键播放/暂停，左右键按固定步长跳转；控件打开时，方向键移动焦点，确定键只激活当前控件。返回键先收起控件，再回列表。 |
| 进度保存 | 复用 `PlayerResumeSyncPolicy` 和 `saveActivity`。现有 `PlayerRoute` 负责触发保存及调用服务端，电视原型要接上离开播放时的保存、资源释放和重新打开时的进度读取。 |

正式 MVP 仍包含基础搜索、简版详情和首页继续观看入口；原型用同一张影片卡片重开来验证进度持久化。首轮交付以一台目标真机为范围，更多设备、字幕/音轨选择和复杂筛选在排期时单独估算。

| **合计** | **3～5** | Debug APK、用例结果和剩余工作量 |

## 验收用例

从干净安装开始。主流程用实体遥控器完成；ADB 可协助安装、采集日志及在模拟器复现按键。表中的时差和次数是本次验收阈值。

| 编号 | 操作 | 通过条件 | 决策权重 |
|---|---|---|---|
| TV-01 | 从电视桌面启动。输入正确地址及 API Key，连接后退出并重启 | 桌面能找到应用，进入页即有可见焦点；软键盘可用遥控器打开、输入和关闭；重启直接进入列表 | 必过 |
| TV-02 | 从干净配置尝试错误 API Key 和不可达地址，随后改正重试 | 明确提示认证或网络错误；能返回输入字段并成功重试；错误状态不会写入有效配置 | 必过 |
| TV-03 | 用方向键跨行并浏览到下一页，从非首行打开影片，再返回 | 卡片高亮始终可见；分页加载后焦点稳定；连续 3 次返回同一张卡片及原滚动区域 | 必过 |
| TV-04 | 直连播放 H.264 样片，连续操作暂停、继续、前进、后退，打开控件后按返回 | 有画面、有声音；每次短按只触发一次动作，跳转方向正确；返回先收起控件，再回列表；离开播放后无残留声音 | 必过 |
| TV-05 | 播到 45～90 秒且离片尾足够远，记下退出时刻；正常返回列表，确认服务器记录后关闭并重启应用，再打开同一影片 | 服务端 `resume_time` 已更新；首次恢复位置与记录的退出时刻相差不超过 5 秒，连续 3 次通过 | 必过 |
| TV-06 | 播放实际 HLS 转码流，再测高负载样片；播放中断网并恢复 | 记录实际流类型、首帧时间、缓冲和错误码。HLS 能稳定播放并完成一次跳转；断网后界面可返回或重试。高负载样片按实际结果标记为直连可用、需转码或待适配 | HLS 结果决定支持范围；可返回或重试必过 |
| TV-07 | 在手机安装常规 Debug APK，用普通入口完成启动、浏览和一次播放 | 进入手机界面并正常播放；共用播放逻辑变更后手机主流程可用 | 必过 |

建议结果表逐项记录用例编号、环境、样片、通过/失败/未测、复现步骤和脱敏证据。首帧、缓冲和跳转耗时至少测三次并注明网络条件，作为下一轮性能目标的基线。

## 验证后的排期决定

- **进入 MVP 开发**。目标真机的必过项全部通过，目标媒体库所需的播放路径可用。保持同包和独立 TV 界面，基于实际改动量更新正式 MVP 的剩余人日。
- **带明确边界进入 MVP 开发**。必过项通过，某个可选设备或格式失败。按已验证的播放范围承诺首版；如果目标媒体库依赖 HLS 或该格式，先修复并复验对应样片。
- **先解决架构或兼容问题**。出现遥控器流程卡死、进度无法保存、基准样片无法播放或手机回归时，先定位到输入/焦点、服务器请求、生命周期、解码或构建依赖。仅在依赖、最低系统版本或发布需求存在明确冲突时评估电视独立构建；设备解码问题先验证现有转码路径。

验收输出包括可安装的 Debug APK、真机与模拟器结果、已验证的设备和流类型、复用或待抽取的代码清单，以及 MVP 剩余工期。正式 MVP 发布前用同一套用例回归，并补测基础搜索、简版详情和首页继续观看。

## TCL 98Q9K 真机试装

实际预览包使用独立构建类型 `tvPreview`，应用 ID 为 `gomeng.dev.stashplayer.tvpreview`，沿用 Android 10（API 29）最低要求。包内的电视 Activity 同时声明 Android TV 和普通桌面启动入口，便于在定制桌面查找。已实现配置、搜索、分页、继续观看列表、遥控器播放和切换播放源，影片卡片直接打开播放器。手机回归使用常规 Debug 构建。

98Q9K 的公开规格列出 Android，具体系统版本以电视固件为准。可在电视设置的「关于本机」查看；如果电视已经开启官方调试并连接到 ADB，可用 `adb shell getprop ro.build.version.sdk` 确认，结果为 29 或更高即可满足最低版本要求。第三方应用安装还取决于电视的安装策略。参考 [98Q9K 规格](https://detail.zol.com.cn/1987/1986154/param.shtml) 和 [TCL 开发者平台](https://developer.tclyun.cn/)。

1. 将 APK 复制到 U 盘，通过电视提供的文件管理或 APK 安装入口打开。安装完成后从应用列表启动 **Stash Player TV**。
2. 输入电视可以访问的 Stash 地址，例如 `http://192.168.1.10:9999`（替换为实际地址）。服务要求 API Key 时填写对应字段。
3. 用方向键选择一部 H.264/AAC 影片。确定键暂停或继续，左右键跳转 10 秒，上下键显示控制条，返回键收起控制条或退出播放。
4. 正常退出播放再重新打开应用，从同一卡片或「继续观看」进入影片，检查恢复位置。再用一部常看的 4K 或 HEVC 影片确认画面、声音、跳转和切换播放源的表现。

## 模拟器验证结果

环境为 Android TV 11（API 30，1080p），使用本机 Stash GraphQL 测试服务、24 条虚拟影片和合成的 H.264/AAC 样片。电视包由 `assembleTvPreview` 生成并通过 APK 签名校验。常规手机 Debug 构建成功，37 项单元测试通过。

- APK 安装并启动成功，系统能查询到电视和普通桌面启动入口。软键盘、地址到密钥的焦点切换、错误密钥提示、正确密钥保存及重启后读取配置已验证。
- 用方向键从第一页进入第二页，焦点落在第一张新卡片。打开第 20 条影片，暂停并跳转，退出后恢复同一卡片焦点。测试服务记录了 51.83 秒的退出进度，应用重启后重新请求同一影片并读回该值。
- 最终 APK 验证了同一影片从直连切到本地 HLS 样流，播放时间从 11 秒推进到 16 秒，返回后仍聚焦原卡片。
- 模拟器以外的多次重复验收见下方真机记录。

- 构建命令为 `gradlew.bat :app:assembleTvPreview --max-workers=2`。输出为 `app/build/outputs/apk/tvPreview/app-tvPreview.apk`，本次交付副本为 `build/outputs/preview/StashPlayer-TV-MVP-20261112.apk`。包名 `gomeng.dev.stashplayer.tvpreview`，版本 `1.13.2-lzcy1.3.0-tv-mvp`，versionCode `59010300`。APK 使用 Debug 签名，本次 SHA-256 为 `B93120642C7DE4414AB5BB645AE26CB4ADB65CE848B7D5DDB216F196BCEA8424`。
- `adb install` 和 `adb install --no-streaming` 均返回 `INSTALL_FAILED_VERIFICATION_FAILURE`；推送到 `/sdcard/Download/` 后电视媒体中心对内部目录停在加载中。电脑监听局域网的文件服务启动请求曾被策略拦截。后续优先使用下述已验证的电视自带多屏互动路径。
- 后续更新沿用 `tvPreview` 构建、相同 application ID 和可用的同一签名密钥，避免卸载已配置的应用。构建后先检查 APK 的包名、版本、签名和目标设备；再通过电视多屏互动发起安装，电视端由用户确认。版本号和签名不匹配导致无法覆盖时，先确认原因和数据保留方案。
- 本次成功路径：用 ADB 连接并完成电视端授权；检查端口未被占用后执行 `adb -s <电视IP>:5555 reverse tcp:18769 tcp:18769`。电脑临时 HTTP 服务只监听 `127.0.0.1:18769`，只提供指定 APK；向电视的多屏互动 TCP 6553 端口发送安装请求，URL 为 `http://127.0.0.1:18769/stash-player-tv.apk`。协议使用四字节大端长度前缀、UTF-8 消息，先发 `159>>1>>0`，再发送来源为 2 的安装请求，包含包名、版本号与 URL 的 MD5；每五秒发送 `150>>` 保持会话。用户在电视提示框选择「同意」后，等待 `PROGRESS` 阶段 5，再用 `pm list packages` 验证。协议及字段参考 [同型号实测记录](https://github.com/pengchujin/aerial-tv/blob/main/docs/devices/tcl-mt5879-cn.md) 和 [参考客户端](https://github.com/pengchujin/aerial-tv/blob/main/tools/tcast-push.py)。
- 完成后关闭临时服务并移除本次 ADB reverse 映射。若端口、IP、授权或电视策略变化，重新检测并根据实际结果调整。
- 本次电视端报告安装成功，ADB 确认包已安装，电视 Activity 启动成功。用户已自行连接真实 Stash 服务器并确认可以正常播放观看；具体格式、续播、多次遥控器操作和断网恢复仍待按用例验证。服务器地址和 API Key 未记录。

## 手机扫码配置电视

从 `1.13.2-lzcy1.4.0` 起，两台设备使用同一局域网。电视在服务器设置里选择「用手机扫码配置」，手机在「设置 → 服务器」选择「扫码发送配置到电视」。手机版读取已保存的配置，电视能连接 Stash 后才保存并打开影片列表。

从 `1.13.2-lzcy1.4.1` 起，手机扫码成功时电视会模糊二维码并显示「已扫码，等待手机确认」。手机点「确认发送」后才传输配置。取消会让仍有效的二维码恢复清晰。手机和电视都需要升级到此版本以支持确认流程。

手机版 `1.13.2-lzcy1.4.2` 在首页刷新图标旁提供「扫一扫」，并以竖屏打开相机。它可以继续和电视版 `1.13.2-lzcy1.4.1-tv-mvp` 配对。

手机用 `assembleRelease` 生成，电视继续用 `assembleTvPreview` 生成。两个 APK 已核对各自的包名和上一版签名，电视覆盖安装仍沿用上述多屏互动流程。二维码包含电视局域网端点和三分钟配对密钥。手机先验证电视持有该密钥，再加密传输配置。配置保存成功后二维码立即失效。
